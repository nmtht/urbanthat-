# ТЗ: Urban That — standalone генеративный редактор города

> Репозиторий: `nmtht/urbanthat-`  
> Кодовое имя пакета: **urbanthat**  
> Версия документа: 2026-09-26 (уточнения после обсуждения стека, visual language, live-preview, масштаба и платформ)

---

## 0. Что это и зачем

Отдельное, независимое приложение для концептуального градостроительного проектирования. Пользователь рисует **кистями** — дороги, зоны — и сразу видит готовую, визуально приятную генеративную **3D-среду**: дорога появляется как отрисованное полотно с полосами и тротуарами по мере того, как её ведут, застройка сама прорастает в зонах по их атрибутам. Референс по ощущению — Cities Skylines (казуальность, немедленный визуальный отклик), но с настоящими урбанистическими атрибутами и метриками, а не игровой абстракцией. Работа ведётся поверх **реального фрагмента карты OSM**, подтянутого как подложка — не с чистого листа в вакууме.

**Жёсткие принципы, от которых нельзя отступать:**

- **Никакой зависимости от Rhino или RhinoCommon.** Это полностью самостоятельное приложение. Импорт из Rhino — опциональная, не приоритетная фича на будущее, не часть MVP.
- **Никакого моста к Unreal.** Визуализация — встроенная часть самого приложения, не отдельный процесс.
- **3D — не поздняя надстройка, а требование с первого дня.** Выбор стека подчинён этому требованию, а не наоборот.
- **OSM-подложка — тоже требование с первого дня**, не опциональная фича на будущее.
- **Кисти — только для дорог и зон.** Застройка **не рисуется вручную** — появляется автоматически, генеративно, как побочный эффект существования зоны с атрибутами.
- **Немедленная визуальная обратная связь.** Пока ведётся кисть — уже видно приблизительный (high-fidelity) результат, а не абстрактную линию, которая «потом» во что-то превратится.

### Visual language

> **«Если бы Apple сделали City Skylines».**

Чистый, сдержанный, премиальный минимализм. Казуальное ощущение города + профессиональный, не-игровой интерфейс. Мягкий свет, аккуратная глубина, стилизованные (не фотореалистичные) материалы. Никакого low-poly «игрушечного» вида и никакого тяжёлого PBR. Типографика и отступы — как в хорошем Apple-приложении.

## 1. Технологический стек

### 1.1 3D-движок — решение и почему

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| **CesiumJS** | OSM-здания и рельеф «из коробки», точная геопривязка WGS84, официально поддерживает Electron | Движок цифрового глобуса, не локальной сцены; дефолтный стиль — фотореализм; данные через Cesium ion | Избыточен для фрагмента города |
| **Babylon.js** | Больше «из коробки» (инспектор, PBR, гизмо) | Меньше готовых OSM→3D примеров | Не даёт решающего преимущества |
| **Three.js** ✅ | Популярен, минималистичен, много примеров «OSM → extrusion», легко стилизовать под казуальный вид | Больше сборки руками | **Выбор** |

**Итог: Three.js** (+ React Three Fiber / Drei для удобства). Сцена — локальная плоская площадка в метрах, центр = `SceneOrigin` (центр выбранного OSM bbox).

### 1.2 Остальной стек

| Слой | Выбор | Почему |
|---|---|---|
| Оболочка | **Electron** | Кроссплатформенность desktop (macOS → Windows) |
| Рендер | **Three.js** + R3F | См. 1.1 |
| Геометрия (offset/union) | **Clipper2** (WASM) | Индустриальный стандарт; вся логика 2D → затем выдавленный 3D |
| OSM | **Overpass API** (+ зеркала) | Без аккаунта, достаточно для фрагмента |
| Проекция | **proj4** (UTM) | lat/lon → локальные метры |
| UI | **React** | HTML-оверлей поверх канваса |
| Состояние | **Command pattern** | Undo/redo с первого дня |
| Формат проекта | **JSON** + `schemaVersion` | Читаемый, версионируемый |

### 1.3 От 2D-геометрии к 3D-сцене

Вся содержательная геометрия (дороги, зоны, связность) остаётся **2D** (Clipper2 на плоскости XY). Three.js — только финальный шаг:

- Дорожное полотно → плоский меш (`y = 0`).
- Здание → `ExtrudeGeometry` по высоте.
- Камера — `OrbitControls` (наклон разрешён).
- Кисть — raycast на плоскость земли (`y = 0`).

### 1.4 Live-preview (уточнение)

| Режим | Когда | Что показываем |
|-------|-------|----------------|
| **High-fidelity preview** | Во время drag кисти | Почти финальное полотно текущего сегмента (ширина, полосы, тротуары, мягкие caps) + снаппинг-подсветка |
| **Full geometry** | На mouse-up / фиксация сегмента | Полный link + hub всех затронутых узлов |

Цель — максимальный реализм ощущения при сохранении 60 fps на сценах 100–300 га. Полный boolean-пересчёт на каждый пиксель движения мыши на больших сценах не допускается.

## 2. Концепция взаимодействия — кисти

### 2.1 Road brush

- Клик-и-тащи; координата через raycast на `y = 0`.
- Во время drag — high-fidelity preview (см. 1.4).
- Снаппинг к узлам сети (и опционально к OSM-дорогам) в пределах `snapTolerance` (0.5 м).
- Пресет = `road_class`.
- При примыкании к узлу — пересчёт hub на mouse-up.

### 2.2 Zone brush

- Лассо или по вершинам.
- Пресет = `zone_type` (цвет заливки).
- После замыкания — метрики в панели + auto-massing.

### 2.3 Застройка — только генеративно

Никакой кисти/кнопки для зданий. Появление — побочный эффект зоны с атрибутами (`far`, `heightMax`, `setbackM`).

## 3. Модель данных

```typescript
interface SceneOrigin {
  lat: number;       // WGS84, точка (0,0) локальной сцены
  lon: number;
  utmZone: number;
}

interface Zone {
  id: string;
  boundary: Point2D[];   // локальные метры
  zoneType: 'residential' | 'commercial' | 'mixed_use' | 'industrial' | 'green' | 'public';
  far: number;
  heightMax: number;     // метры
  setbackM: number;
  greenRatio: number;
}

interface RoadEdge {
  id: string;
  centerline: Point2D[];
  roadClass: 'primary' | 'secondary' | 'local' | 'pedestrian' | 'bike';
  lanes: number;
  widthM: number;
  sidewalkWidthM: number;
  startNodeId: string;
  endNodeId: string;
}

interface RoadNode {
  id: string;
  position: Point2D;
  degree: number;
  nodeType: 'dead_end' | 'through' | 'intersection';
}

interface Building {
  id: string;
  sourceZoneId: string;
  footprint: Point2D[];
  floors: number;
  farActual: number;
  farTarget: number;
}
```

- Все линейные размеры — **метры**.
- `FLOOR_HEIGHT_M = 3.3` (константа, в будущем настраиваемая).
- JSON проекта содержит `schemaVersion`.

## 4. Алгоритмы — портировать, не проектировать заново

### 4.1 Граф дорожной сети

Концы полилиний в пределах `snapTolerance` (0.5 м) → узлы (union-find). Степень: 1 = тупик, 2 = проходной, 3+ = перекрёсток.

### 4.2 Геометрия полотна — link + hub

- **Link**: оффсет центральной части (между `extensionDistance` от узлов) на `±width/2`, без boolean.
- **Hub**: в узле для CCW-соседних пар — **левый борт первого + правый борт второго** (критично не перепутать стороны). Объединение hub-полигонов через Clipper2.
- Острые углы (<20°) — принятый предел; мягкое предупреждение в UI допустимо.
- Юнит-тесты на крест, T, Y, острый угол — обязательны.

### 4.3 Валидация сети

Тупики, разрывы, самопересечения — мягкие визуальные подсказки, не блокирующие ошибки.

### 4.4 Зоны — метрики и massing

- Площадь — формула шнурков.
- `buildableAreaSqm = area × far`.
- Контур застройки = `boundary.offset(-setbackM)`.
- `floors = ceil(buildableArea / footprintArea)`, clamp по `heightMax / FLOOR_HEIGHT_M`.
- Доступ к дороге — сэмплирование границы, min distance до полигона дороги.

## 5. Интеграция OSM

### 5.1 Выбор фрагмента

Адрес/координаты или мини-карта (Leaflet) в диалоге импорта → bbox → `SceneOrigin` = центр bbox.

### 5.2 Overpass

Публичный `https://overpass-api.de/api/interpreter` + фолбэки (`overpass.kumi.systems`, др.). Таймауты и понятный UX при ошибках/rate-limit.

```
[out:json][timeout:25];
(
  way["building"](south,west,north,east);
  way["highway"](south,west,north,east);
);
out geom;
```

### 5.3 Проекция и подложка

1. proj4: `{lat,lon}` → локальные метры относительно `SceneOrigin`.
2. `building` → выдавливание (дефолт 9 м / 3 этажа, если нет height/levels), **приглушённый нейтральный материал**.
3. `highway` → упрощённые линии (фоновый контекст, не через link+hub).
4. Слой `OsmContextLayer` — некликабельный, недоступный для кистей.

### 5.4 Снаппинг к OSM

Опционально (галочка в настройках кисти): прилипание road brush к геометрии OSM-дорог.

### 5.5 Актуальность

Снепшот на момент импорта. Кнопка «Обновить подложку» — повторный запрос. Без фоновой синхронизации.

## 7. Нефункциональные требования

| Требование | Значение |
|------------|----------|
| **Платформы MVP** | macOS (приоритет) + Windows |
| **iPad / tablet** | **Вне скоупа MVP** (требует другого стека или серьёзных компромиссов) |
| **Размер сцены** | До **500 га** комфортно, запас до ~1000 га |
| **Производительность** | 60 fps при орбите и drag на 100–300 га; на 500+ га допустимо 30–40 fps без подвисаний |
| **Память** | Целевой бюджет ~1.5–2 GB на проект 500 га |
| **Открытие проекта** | < 3–4 сек для типичного 500 га |
| **Оптимизация** | С первых спринтов: пространственный индекс, dirty-флаги, частичный пересчёт hubs, кэш мешей, InstancedMesh для зданий |

## 8. MVP — порядок реализации

1. **Импорт OSM** — bbox, Overpass, проекция, приглушённая 3D-подложка.
2. **3D-сцена и камера** — вьюпорт, OrbitControls, плоскость земли, raycast.
3. **Road brush без перекрёстков** — live high-fidelity preview (только link).
4. **Граф + снаппинг** — узлы, в т.ч. опциональный снаппинг к OSM.
5. **Hub-геометрия** — «left A + right B», тесты на типовых углах.
6. **Zone brush** — рисование + метрики.
7. **Auto-massing** — здания сразу после зоны.
8. **Полировка визуала** — материалы, свет (Apple × City Skylines).
9. **Save/load** — JSON + schemaVersion + OSM-снепшот.

**Критерий готовности MVP:** пользователь выбирает реальный участок на мини-карте, видит OSM как 3D-подложку, рисует дороги (со снаппингом) и зоны, видит корректные перекрёстки и автоматически появившуюся застройку — всё в 3D с управляемой камерой, без кнопки «generate».

### Предлагаемые спринты (2 недели)

| Sprint | Фокус |
|--------|--------|
| 0 | Репозиторий, Electron+Vite+React+TS+Three, пустая сцена, command stack skeleton |
| 1 | OSM-подложка end-to-end |
| 2 | Road brush (link only) + кэш геометрии |
| 3 | Граф, снаппинг, hub-геометрия + юнит-тесты |
| 4 | Zone brush + auto-massing |
| 5 | Оптимизация под 500 га, визуал, save/load |

## 10. Ключевые технические решения (зафиксировать сразу)

1. Preview vs Final geometry (см. 1.4).
2. Dirty-флаги на узлах/рёбрах — пересчитывать только затронутое.
3. Пространственный индекс (хотя бы grid 50×50 м) для снаппинга и поиска дорог.
4. Здания — `InstancedMesh` / батчинг с первых итераций massing.
5. `schemaVersion` в JSON проекта с первого save.
